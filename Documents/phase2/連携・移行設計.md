# entry連携・移行・受入設計

2026-10-27 / 設計案。実装・本番照合・DDL実行は未実施。

## 1. 参照と更新の契約

同一DBの共通PHPサービスを第一案とし、内部連携のためだけのHTTP APIは初期導入しない。manageとentryが同じサービス版を利用する。公開JSONエンドポイントは必要性が確認された時点で追加する。

| サービス | 入力 | 出力・制約 |
| --- | --- | --- |
| Identity.resolve | セッションuid | DB認証状態、旧互換ロール、portal権限。存在しない/停止ユーザーを拒否 |
| Authorization.require | actor、permission、club_id/対象ID | 例外または許可。UIでボタン非表示だけでは済ませない |
| Profile.read/update | actor、subject、version、変更列 | ポータル正本プロフィール。氏名/生年月日や番号変更の制約を検証 |
| Eligibility.forEvent | user_id、portal_event_id、評価時刻 | member_type、membership_id、member_paid、member_active、所属、期間、制度別資格、判定理由、source_mode |
| Billing.issue/allocate/reverse | actor、申請/請求/入金ID、冪等キー、version | トランザクション結果。自己申告/決済リンク遷移で支払済みにしない |
| Affiliation.decide | actor、membership、club_year、判断、version | 担当範囲・年度・クラブ承認確認。履歴、番号更新、監査、通知を同時記録 |

EligibilityはUI表示、POST保存、費用計算、管理者修正すべてから呼ぶ。ブラウザーが送る「登録済」「paid」を信頼しない。DB障害時は「未加入」として会費を再請求せず処理保留/503。メール障害はoutboxで再送する。

## 2. 支払ビューの扱い

現行 `view_annual_jmrc_payments` は `user_id,target_year,is_member_paid,is_mutual_aid_paid` を返す。ダンプではacceptedなentryに対し、個人会員選択と共済費目名からMAXで判定し、実際の入金充当を確認していない。

設計判断:

1. Generalの年度会費に限り、portal請求の有効な充当が全額を満たす状態からmember_paidを返す。所属/資格停止とは分け、member_activeを別返却する。会費支払済みでも資格未成立はあり得る。

   移行確認済みの会費支払証拠も出所付きで別評価する。免除等の支払不要資格はmember_paidとは分け、member_activeと判定理由で表現する。既存の二値列だけで表せないケースはforEventへ切り替えるまで対象導線を公開しない。
2. Temporaryの一回500円を年会費支払済みフラグへ集約しない。年度ビューではイベント当日資格を表現できないため、必ずforEventを使用する。
3. R10（2026-10-28回答）により、協議会見舞金（JMRC近畿）、救済基金（ジムカーナ部会）、スポーツ安全保険（JMRC近畿が代理店）は独立制度として扱う。請求・入金充当・加入資格・有効期間を制度別に管理し、他制度の支払や資格を流用しない。is_mutual_aid_paidの既存救済基金判定は維持し、保険・協議会見舞金の支払を代入しない。救済基金の正本移管先と各制度の詳細条件は未確定。
4. 最初に別名の比較用projection（例 `portal_annual_payment_status`）を作り、旧ビューと差分を照合。既存名のCREATE OR REPLACEは実施しない。
5. 切替年度を明示し、旧年度は従来の情報と出所を維持、新年度はportal正本を参照。年度内に都合よく両方をORして資格付与しない。
6. 既存名の互換ビューは残存参照向けに列/型/年度/行なし時の扱いを固定して提供する案。最終DDLとDEFINER/SQL SECURITYは実機権限確認後。新機能はビューだけに依存しない。

## 4. プロフィール同期

portal移行前はentrantsを初期移行元とし、user_idを保持してportal_profilesへコピー。免許/ライセンスはidentifiersへ種類別に取り込み、空欄/重複/書式不正はレビュー対象。clubs/jmrc_affiliated_clubsのコードを末尾5桁だけで無条件統合しない。

正本切替後はportalのみが共通プロフィールを更新する。entryの読み取りをサービスへ切替し、どうしてもentrantsを読む旧経路には同一DBトランザクションで互換投影を行う。投影は一方向、row_versionと監査付き。entry固有列（車両等）を上書きしない。

既存entrantsはlicense_no/license_expiry/birthday等がNOT NULLのため、免許なしの人にダミー免許証番号や日付を入れない。portal上は登録可能なプロフィールを保持し、entryへ参加する際は競技要件を別検証する。投影できないケースはサービス読取りへの切替が完了するまで該当導線を有効化しない。

## 5. 移行段階

| 段階 | 内容 | 戻し方 |
| --- | --- | --- |
| 0 読取調査 | preflight SQL、本番コード/DBの版、PHP/session、バックアップと復元試験 | 本番変更なし |
| 1 追加のみ | portalテーブル、明示権限、マスター、移行台帳。DDLは専用管理ユーザー | 新領域を未使用化、既存経路継続 |
| 2 shadow | 冪等な初期移行、番号/金額/資格の差分、受取人等の出所を確認 | source_modeをlegacy維持、移行バッチ再実行可能 |
| 3 ステージング | 両アプリの認証・全書込切替・CSV/帳票・年度境界を受入 | 本番に影響なし |
| 4 限定切替 | 新年度クラブ/個人先行受付、source_modeを年度単位でportalへ。旧経路は新年度の書込拒否 | 新申請停止、書込整合性確認後にのみ戻す |
| 5 正式公開 | manage導線、運営手順、監視、情報移行、旧経路の段階縮退 | 公開停止とデータ保全、必要なら共通サービスを継続利用 |

DDLはMariaDBで暗黙commitを伴うことがあるため、トランザクションだけを復旧手段にしない。旧ビュー定義・コード・設定を版付き保存し、スナップショットを隔離DBへ復元して検証する。移行スクリプトはmigration keyとsource hashで二重取込を防ぐ。

既存is_jmrc_member/type_a/type_b/登録済は支払証拠にしない。出所、年度、明細、実入金、事務局確認を突合して migration_pending/confirmed を区別する。移行確認済み資格は元データIDと承認者を記録し、架空の銀行入金を作って辻褄を合わせない。

**新領域に入金・申請ができた後は、フラグだけlegacyへ戻せない。** その間の全操作を台帳と照合し、旧経路の二重請求を止めた状態で整合を回復する。保険の外部提出や実返金はDB復元だけで取り消せないため、別途事務局の訂正業務が必要。復旧のために新記録をDROPしない。

## 6. 配置・運用条件

URLは `/manage/`、既存 `/entry/` と同一ホスト。DocumentRoot/実体パス/転送/PHP実行主体は本番確認待ち。ランタイムDBユーザーへDDL権限を与えない。共通認証に必要な既存usersの参照/更新権限とportal業務権限を列挙し、マイグレーション用資格情報と分離する。

共通設定はWeb外、リポジトリへ秘密を保存しない。帳票・保険ファイルは権限確認したダウンロード経路のみ。ステージングはアクセス制限し、メール/決済リンク/定期処理を本番宛に誤実行させない。本番データのマスキング不要という運営回答を、メール配信許可と解釈しない。
