# 本番初回導入と復元手順

対象はgymkinki.comの/manage/と既存/entry/。2026年10月29日、ユーザーから「既存ユーザーがそのままサインインできること」「復元手順を整理して本番へ適用すること」の指示を受けた。

## 保持する情報

既存usersのID、メールアドレス、パスワードハッシュ、旧role_idを保持する。本人に再登録やパスワード再設定を要求しない。追加するportal_account_controlsは既存usersから作成し、ポータルの事務局権限は別途指定されたアカウントにだけ付与する。旧管理者ロールからの自動昇格は行わない。

同じPHPSESSIDと保存先を使用する。切替時に旧形式の認証済みセッションを引き継げるのは、導入後1時間の限定期間だけ。有効な既存ID、現在のDBの確認済みメール、active状態、旧セッションの正しいrole_id・verifiedを確認する。引継ぎ後はパスワード変更と認証版による失効を適用する。新形式セッションの欠落・改竄を旧形式として再認証しない。既存CSRFを保持し、入力中のフォームへの影響を抑える。旧セッションの保存先はPHP-FPM実行ユーザーの0700に制限する。

新規登録時は旧register_handlerのトランザクション内で認証状態を作成する。未確認の再登録はIDを維持するが、停止状態や既存ポータル情報・競技会履歴がある場合はプロフィール削除を実行せず事務局確認へ回す。メール確認とパスワード再設定の既存コードは変更しない。

## バックアップと復元試験

本番内の保存先は次のとおり。外部へデータを持ち出していない。

`/var/www/vhosts/gymkinki.com/private/jmrc-portal-backups/20261029T092700Z/`

- database.sql.gz: InnoDBの単一トランザクションによる業務DB全体のバックアップ。
- entry.tar.gz: 設定・セッションを含む既存entryのバックアップ。
- manifest.json: バックアップと対象コードのSHA-256、ユーザー情報の集計ハッシュ。
- portal-auth.config.php: 導入時に生成した暗号鍵・新DB接続設定の控え。導入前バックアップにはないため、生成後に追加保存する。
- deployment.json: 適用段階と切替対象ファイルの記録。

保存ディレクトリはrootの0700、バックアップは0600。秘密と個人情報を含むため、Git・公開領域・回答資料には内容を掲載しない。

バックアップを専用の別DBへ復元し、34オブジェクトの生成と、305ユーザー・確認済み296ユーザーの集計、ID・role_id・確認状態・パスワードハッシュの集計一致を確認した。復元試験用DBは終了後に削除済み。業務DBを復元試験先に使用していない。

## 初回配置

scripts/install_initial_production.pyは初回導入専用。stageとbackupの絶対パス、リリースのコミットIDを指定してrootで実行する。バックアップ時からの本番コード変更、未検証のstage、既存manageや既存portal表を検出すると停止する。

1. 追加DDL 001～010を順番に適用する。DDLは暗黙commitを伴うため、途中まで適用された場合は記録を確認し、最初から再実行しない。
2. 既存usersへ認証状態を追加し、旧entrantsのプロフィールをportal_profilesへ複写する。ライセンスの暗号移行や資格の有効化は自動実行しない。
3. 専用実行DBユーザー、Web非公開設定、暗号鍵、バージョン付きソースを配置する。実行DBユーザーへDDL権限を与えない。権限マスター・ロール付与の更新権限も与えない。
4. 既存コードを退避済みのハッシュと照合し、追加helper、登録処理、会費連携、認証、CSRF、ログイン・ログアウトを一時ファイルから置き換える。
5. 公開ファイルだけを/manage/へ配置し、非公開コード・設定・帳票原本を公開ディレクトリへ置かない。
6. HTTPSで共通ログイン、旧画面表示、共通ログアウト、不正CSRF拒否を確認し、既存ユーザーの認証情報の集計ハッシュを再照合する。

2027年度の日程はshadowで登録し、資格情報の参照先をportalへ切り替えない。実会費、クラブ対応、ライセンス移行、入金照合が揃うまで旧エントリーの支払判定を維持する。ライセンス本人更新、保険意思受付、銀行CSVは初回導入では無効。ユーザーが指定した事務局アカウントには明示権限を付与し、入金先設定と本人情報訂正を利用可能にする。その他は実データの確認後に必要な機能から有効化する。保険の正式加入、個人情報削除、外部メール配信は開始しない。

## 通常の切戻し

新しい申請・請求・入金がまだない初回導入中は、次の手順で旧entryコードへ戻す。

```bash
sudo python3 /var/www/vhosts/gymkinki.com/private/jmrc-portal-backups/20261029T092700Z/restore_initial_production.py \
  --backup /var/www/vhosts/gymkinki.com/private/jmrc-portal-backups/20261029T092700Z
```

実行前にrestore_initial_production.pyをGitの保存版と照合する。スクリプトは新しい申請・請求・入金の存在を確認し、存在すれば機械的な切戻しを拒否する。旧コードをバックアップのハッシュで検証しながら戻し、manageはバックアップ領域へ移動して公開停止する。DBのDROP、業務データの削除、全DBの上書き、セッションの巻戻しは行わない。追加表と暗号鍵も保持する。

旧認証コードは引き続きuid・ridを使えるため、切戻しのためにusersやパスワードを更新しない。復元後はログイン画面、既存競技会画面、ログアウトを確認する。

## DB障害時の復元

新しい業務記録がある場合、最初にポータル受付を停止し、障害発生時点のDBと変更履歴を別名で保全する。database.sql.gzは別DBへ復元して照合し、切替後の申請・入金・既存entryの更新を特定してから、対象を限定して復旧する。稼働中のjmrckinkiへバックアップをそのまま流し込まない。

全DB復元が必要な障害では、書込み停止時間と失われる更新を明示したうえで実施する。バックアップ後のエントリー・入金まで失うため、通常のコード切戻しの代用にはしない。旧コードへ戻すためだけに追加portal表を削除しない。

## 適用前の検証記録

既存ユーザーの認証情報を変更せず、旧登録処理による新規登録、同じIDでの未確認再登録、メール確認、共通サインイン、旧パスワード再設定、セッション失効、停止・既存記録を守る再登録拒否、旧セッション引継ぎを隔離HTTPSで検証した。メール送信だけは隔離用の代替処理に置き換え、外部送信していない。

最終結果はHTTPS 666項目、QR・画面更新25項目、Excel独立照合32項目、実ブラウザー62項目、合計785項目PASS。PHP構文確認82ファイル。既存jmrckinki原本のソースは変更していない。

本番検証にはユーザーが指定した既存アカウントを使う。一時検証ユーザー・架空の申請・入金は本番に作成しない。パスワードは検証プロセスの標準入力からだけ渡し、ファイルや資料へ保存しない。ログインに伴う通常のセッション・監査記録は残る。旧セッション引継ぎと新規登録の書込み試験は隔離環境で実施し、本番では新規登録やメール送信を試さない。

## 本番適用結果

初回導入を実施した。共通認証・登録互換・初期導入コードは36e5e17、匿名照会の既定パス修正を含む配置版は076a4b1。追加DDL 001～010を適用し、2027年度はshadowで登録した。指定された既存ユーザーID 3に事務局権限を付与した。既存usersのrole_idやパスワードは変更していない。

初回のHTTP確認で、環境変数が渡らないPlesk環境において匿名QR用bootstrapだけが503になる箇所を発見した。既定の非公開パスを設定して修正し、配置済みファイルを更新した。既存entryの認証・データには影響させず、修正後に全16項目の本番確認が通った。環境変数なしの公開・非公開bootstrap確認も隔離検証へ追加した。

指定された既存アカウントで、実サインイン、既存競技会画面、同じセッションでのmanage表示、事務局の入金先設定・本人情報訂正画面の閲覧、不正CSRF拒否、共通ログアウトを確認した。本番に検証用ユーザー、申請、入金は作成していない。ユーザーから渡されたパスワードはファイルへ保存していない。

既存users、roles、entrants、clubs、jmrc_affiliated_clubs、jmrc_annual_memberships、jmrc_events、jmrc_entries、jmrc_entry_feesの9表について、適用前バックアップを別DBへ復元してデータチェックサムを比較し、全表で一致した。ユーザー305件、エントリー1,200件、費用明細1,508件を保持している。別DBは比較終了後に削除した。

本番配置のPHP・JS・CSSと既存entryへの差替えコード50ファイルは、ローカルの配置元とSHA-256が一致した。既存のconfig.php、db.php、verify.php、reset_handler.phpは変更していない。サーバー全体の再起動や公開入口の変更は行っていない。

機械可読の結果は[本番確認記録](production_20261029_result.json)を参照。銀行CSV・ライセンス本人更新・保険意思受付は本番で無効のまま。登録受付と年度資格の参照先切替も未実施であり、本番の稼働開始条件がすべて揃ったという意味ではない。

環境変数なしの既定パス確認3項目を含む最終隔離検証は788項目PASS、PHP構文確認82ファイル。本番確認は別途16項目PASS。復旧スクリプトも上記バックアップディレクトリにroot限定で保存した。
