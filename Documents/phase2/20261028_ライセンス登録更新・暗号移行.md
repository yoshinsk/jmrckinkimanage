# ライセンス情報の登録・更新と暗号移行

2026-10-28。本人のJAFライセンス登録・更新、旧データからの確認付き暗号移行、会員証・QRへの反映を実装しました。本番・既存jmrckinki原本は変更していません。

## 本人が登録・更新し、他人の番号にはアクセスさせない

`/manage/licenses.php`で本人のJAF競技・審判員ライセンスを登録します。登録済み一覧には区分・種類・期限だけを表示し、編集対象を選んだ場合に本人へ番号を復号表示します。事務局・財務・クラブ代表という理由で、他人の番号を通常画面から編集・参照できる権限は追加していません。

番号、ライセンス種類、期限を更新できます。競技/審判員の区分は登録後に変更せず、別区分は別レコードとして登録します。更新版数が違う場合は409で止め、他の操作を上書きしません。同じ区分・同じ番号の既知の重複候補は自動統合せず、事務局確認へ回します。

番号は`gcm1:`形式のAES-256-GCMで保存し、認証データを`jmrc:identifier:v1:<識別レコードID>`とします。検索・重複判定にはHMACを使います。更新前の情報も別の認証データで暗号化して履歴へ保存し、通常の監査・通知予約には番号を含めません。

## 期限更新では既存QRを維持し、番号変更では旧QRを失効する

| 更新内容 | 会員資格・会員証・QRへの反映 |
| --- | --- |
| 同番号・同種類の期限更新 | 暗号文と会員番号を維持。期限切れで資格・表示を無効にし、条件復旧時には失効されていない同じQRを再評価 |
| 番号またはライセンス種類の変更 | 旧QRを失効。会員証の採番元変更を検出し、自動再発行を止める |
| 同じ値の再送 | 更新履歴・監査を重複作成しない |
| 不明な旧保管形式 | 平文扱いせず、通常更新を止めて移行確認を求める |

資格の再判定、番号/種類変更時のQR失効、更新履歴・監査は同じトランザクションで記録します。本人の申請・所属・入金の承認を勝手に付け直す処理はありません。未確定の会員番号再発行方針と公開項目も引き続き保留です。

JAFへのオンライン照合は行いません。期限が不明な場合は推定せず未登録として運営確認を求めます。移行で期限を未登録にする場合も、確認ファイルで明示する必要があります。

## 移行元は旧entrantsのJAF項目に限定する

既存コード`jmrckinki/httpdocs/entry/common/functions.php`のプロフィールからエントリーへの対応と、既存スキーマを確認しました。

| 移行元 | 用途 |
| --- | --- |
| `entrants.user_id` | 既存共通ユーザーとの対応 |
| `entrants.jaf_license_no` | JAF番号 |
| `entrants.jaf_license_type` | ライセンス種類。競技/審判員の区分はこの文字列から自動判定しない |
| `entrants.license_no` / `license_expiry` | 運転免許の情報なので移行しない |

今回の移行はポータル側の暗号化登録です。旧`entrants`への書き戻し、旧データの削除、競技会履歴の変更は行いません。稼働中の旧エントリーが参照する平文項目は残ります。全システムから平文を除去した状態ではなく、旧画面の参照先切替や削除は別工程です。

既存ポータルの不明形式を置き換える場合も、旧JAF情報との対応、対象識別レコードID、現在の更新版を明示して確認します。別人のID、別区分、古い更新版では適用しません。

## planで暗号計画を作り、check後に明示applyする

移行CLIは[Web非公開のスクリプト](../../scripts/license_migrate.php)です。OSと非公開設定へのアクセスを許された保守担当者が実行します。`--actor`は監査上の実行者IDで、通常Webログインの代わりになる認証手段ではありません。事務局の承認済みglobal grantと`identifiers.migrate`権限も必要です。

1. バックアップ・復元手順、対象ユーザー、DB、非公開保存先を確認します。非公開の`JMRC_AUTH_BOOTSTRAP`と`JMRC_AUTH_CONFIG`、32バイト鍵の`data_key`を設定します。
2. `plan`で暗号化した計画ファイルと確認雛形を作ります。DBはSELECTだけです。1計画500件以内に分割し、公開ディレクトリやクラウド共有先へ保存しません。既存ファイルは上書きしません。
3. 確認雛形の各候補について`approve`または`skip`を指定します。`approve`には競技/審判員の区分、期限確認、期限または明示したnullが必要です。JAF番号の原文は、権限のある旧画面等で別途確認します。確認ファイルには番号を記入しません。
4. 既存の識別情報へ適用する場合は`target_identifier_id`と`target_version`を指定します。既存行があるのに移行先を省略した場合は止めます。新規行を自動で別アカウントへ統合しません。
5. `check`で計画・確認内容、DB、元データの変更、移行先の所有者・区分・版、重複候補を検査します。DBは書き込みません。実行時の条件を再検査するため、check成功後もapplyの成功を保証するものではありません。
6. `apply`と`--apply`を両方指定した場合だけ適用します。全対象が成功した場合にcommitし、途中の不備や監査障害では全件をrollbackします。

以下は**検証用コンテナ内で用いた値の例**です。DB・実行者・パスは本番設定ではありません。通常は検証終了時に環境と一時ファイルを削除します。本番の実行パス・対象DBは導入時に改めて確認してください。

```sh
php /srv/auth/scripts/license_migrate.php --mode=plan --actor=7 \
  --expected-database=jmrckinki_auth_lab --users=30,31 \
  --out=/tmp/jmrc-license-plan.json --review-out=/tmp/jmrc-license-review.json

# 確認ファイルを編集した後
php /srv/auth/scripts/license_migrate.php --mode=check --actor=7 \
  --expected-database=jmrckinki_auth_lab \
  --manifest=/tmp/jmrc-license-plan.json --review=/tmp/jmrc-license-review.json

php /srv/auth/scripts/license_migrate.php --mode=apply --apply --actor=7 \
  --expected-database=jmrckinki_auth_lab \
  --manifest=/tmp/jmrc-license-plan.json --review=/tmp/jmrc-license-review.json
```

確認ファイルの一項目は次の形式です。`target_identifier_id`がnullなら新規登録です。期限不明を勝手に「無期限」と解釈せず、運営確認が済まない候補はskipしてください。

```json
{"user_id":30,"decision":"approve","kind":"jaf_competition",
 "expiry_reviewed":true,"expires_on":null,
 "target_identifier_id":null,"target_version":null}
```

計画後に元のJAF情報が変わった場合は409で止めます。同じ計画・確認内容の再実行は適用済みとして変更しません。適用後のレビュー差し替えも拒否します。計画ファイルの改変や別計画の確認ファイルとの混在を認証付き暗号とバッチIDで検出します。

`apply`は整合性確認の間、元レコードへ共有ロックを取ります。元データは変更しませんが、その間の旧画面の更新は待つ可能性があります。将来の実移行では受付と重ならない時間帯を選び、小分けで実行してください。

## 006適用と移行確認後に本人受付を開く

本番は未実施です。[006](../../design/phase2/006_license_management.sql)と[移行権限SQL](../../design/phase2/license_permissions.sql)を適用し、事務局担当者のgrantを確認する必要があります。DB実行権限は識別情報・重複確保のINSERT/UPDATE、暗号履歴・移行記録のINSERT等へ限定します。旧データのUPDATE/DELETEや新しい金融記録の削除権限は追加しません。

新しい重複確保は、移行済み・新規登録の正規HMACを対象とします。不明形式の旧レコードを放置したままでは、既存全件との重複判定は保証できません。移行・重複確認後に`JMRC_LICENSE_SELF_SERVICE=1`、または非公開設定の`license_self_service_enabled=true`として本人受付を開きます。既定は無効です。

暗号鍵、暗号計画、確認ファイルはWeb非公開で管理し、WindowsではNTFSのアクセス権も確認してください。CLIの0600指定だけをWindowsのアクセス制御の代替にしません。鍵の更新や過去履歴の削除は、未確定の再発行・保管方針と併せて別途決めます。

## スマートフォン相当の実Chromium・WebKitで検証する

```powershell
npm.cmd ci --prefix tests/card --ignore-scripts --no-audit --no-fund
python tests/auth/validate_auth.py
```

PHP-FPM/HTTPS/MariaDBの統合検証と、[Playwright公式Dockerイメージ](https://playwright.dev/docs/docker)を固定した実ブラウザーを使います。ブラウザー用の固定npm依存はDockerビルド時に準備します。実行時はDocker internalネットワークだけで、公開ポート・本番データはありません。

[端末エミュレーション](https://playwright.dev/docs/emulation)はChromiumのPixel 7相当とWebKitのiPhone 13相当です。ライセンスの登録・期限更新、General申請・承認・入金から会員証への連携、描画したQRの復号、匿名照会、期限切れと復旧、番号変更、通信断時の表示消去、縦横画面を確認します。画面幅・タッチ対応と実際のtap操作を検証し、実際の描画画像も目視確認します。

結果・ブラウザー版・各ケース・対象ソースのハッシュは[検証記録](../../tests/auth/validation_result.json)、架空データの画面画像は`tmp/mobile_validation/`へ保存します。画像に出てくる番号や会員は架空です。物理端末のカメラ、実JAF情報の真正性、実決済・本番移行は未検証です。

最終結果: HTTPS 434項目（既存382＋登録/移行52）、QR・DOM模擬23項目、実ブラウザー28項目、合計485項目PASS。PHP構文確認60ファイル。Chromium 156.0.8078.4はPixel 7相当の幅412、WebKit 27.2はiPhone 13相当の幅390で検証しました。WebKitの`maxTouchPoints`は0ですが、タッチイベント対応と実際のtap操作を確認しています。原本ソースはハッシュ不変で、専用コンテナとネットワークの削除も確認しました。
