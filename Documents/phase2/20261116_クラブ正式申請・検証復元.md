## 復元手順

1. 受付停止と現在のコード・DB・業務件数・設定を読み取り、適用記録と比較します。配置後の変更がある場合は自動復元せず、その変更を保全して対象を再確認します。
2. 先にファイルを復元します。以下のコマンドは保存済みの21ファイルだけを対象にします。新規ファイルを除去し、既存ファイルと所有者・権限を戻して、対象PHPのキャッシュを失効させます。

   ```sh
   sudo python3 /var/www/vhosts/gymkinki.com/private/jmrc-portal-backups/club-intake-20261116-20261116T034527Z/deploy_information_preview.py --rollback /var/www/vhosts/gymkinki.com/private/jmrc-portal-backups/club-intake-20261116-20261116T034527Z
   ```

3. 追加表の申請と履歴が0件、既存業務表と権限が適用直後と同一である場合だけ、追加DBを戻せます。以下は追加3表と今回追加したDML権限だけを除去します。申請や後続の既存業務変更があれば拒否します。その場合、3表は保持したまま調査します。

   ```sh
   sudo /opt/plesk/php/8.4/bin/php /var/www/vhosts/gymkinki.com/private/jmrc-portal-backups/club-intake-tools-20261116-20261116T034500Z/scripts/club_intake_database.php --rollback /var/www/vhosts/gymkinki.com/private/jmrc-portal-backups/club-intake-db-20261116-20261116T034500Z
   ```

4. 既存サインイン、entryの表示、受付状態、業務表・設定のハッシュを読み取り確認します。DB全体の `before.sql` を通常の復元で上書き投入しません。後続の本番データを失うため、全体復元が必要な障害では別途影響を確認します。

復元は隔離環境で検証済みです。本番で試験目的の巻き戻しは行っていません。配置前後のハッシュ、テスト、Push先と配置内容の照合は今回の検証記録とコミットに対応付けます。
