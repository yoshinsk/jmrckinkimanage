# 共通認証アダプター実装・隔離検証

2026-10-27。対象は既存`/entry/`と新`/manage/`。本番には接続・変更せず、隣接jmrckinkiの原本も変更していない。

## 実装

- [共通認証](../../src/Auth/SharedAuth.php): 既存users/パスワードによる認証、セッション、CSRF、状態/認証版/パスワード変更の再確認。
- [互換ブリッジ](../../integration/jmrckinki/README.md): 旧auth_* API、ログイン戻り先、GET確認/POST実行の共通ログアウト。
- [manageの最小認証画面](../../public/manage/index.php): 共通IDでログイン状態を表示。業務機能は別工程。
- [再現手順](../../tests/auth/README.md) / [機械可読結果](../../tests/auth/validation_result.json)。

認証資格情報を複製せず、旧role_idを変更しない。portalの追加権限はscope/承認/有効期間付きgrantだけから取得する。メール未認証・停止・controls欠落・版なし旧セッションを拒否する。ログイン済みであることをGeneral/Temporary資格成立とは扱わない。

## 検証構成と範囲

PHP-FPM 8.4.27、nginx HTTPS、MariaDB 10.5.29を専用Docker internalネットワークで起動。公開ポートなし。自己署名TLSを検証クライアントで検証し、HTTPSのSecure/HttpOnly/SameSite=Lax/path=/を確認する。架空データのみを使い、認証用ランタイムDB権限とfixture管理権限を分離した。

既存の共通header/footer/functions/dbと3ロールの競技会一覧GETは、隣接リポジトリの実ソースを隔離コピーして使用した。auth/csrf/login/logoutは互換実装へ差し替えた。これは未改修の本番へ接続して行う試験ではない。

検証はHTTPレベル。ブラウザーのJSや外観、競技会POST、メール、帳票、会計の回帰は未実施。専用のidentity/permission観測経路は検証用にのみ配置し、本番公開用コードに含めない。

## 結果

**99項目すべてPASS、PHP構文確認24ファイルで成功。** ソースSHA-256と各ケースは機械可読結果を参照。以下を確認した。

| 対象 | 確認結果 |
| --- | --- |
| 旧3ロール | 旧既定先を維持し、既存競技会GETが200。新規/ログイン済みの双方からmanageへ復帰 |
| 共通ID | 両アプリで同じuid/rid/verified。旧role_idをportal権限に合わせて変更しない |
| セッション | ログイン時にID/CSRF更新。版なし/破棄後ID再送/偽の旧ridキャッシュで昇格不可 |
| 共通ログアウト | manageとentry双方のPOSTで共通失効。GET実行や異なるセッションのCSRFを拒否 |
| 権限 | 自クラブのみ、明示global/複数ロール、未承認/未来/期限切れ/取消を検査。旧JMRC_ADMINも自動昇格なし |
| アカウント状態 | メール未認証・停止・controls欠落を拒否。認証版/パスワード変更で別ブラウザーも失効 |
| 戻り先 | 危険URL/改行/相対逸脱/不明キー/配列を拒否。既存公開一覧のevent_id付き申込nextは維持 |
| 障害 | 認証/認可DB障害は503。監査故障で新ログインを成立させず、ログアウトは失効処理を行う |
| 監査 | ログイン/拒否/ログアウトを保存。パスワード・メール・セッションIDを記録しない |
